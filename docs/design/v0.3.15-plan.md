# v0.3.15 plan — skills as Aurora's operating system (plan)

Status: **draft** (2026-06-10). Big-changes line; **plan only, no code yet.**
Scope is large enough that this doc proposes a **phased split** rather than
promising all of it in one version.

## The vision (from the user)

Aurora should run itself through **skills**, choosing the right one by what the
message is:

- Each skill can be **individually enabled/disabled**; Aurora picks among the
  _active_ ones.
- **Aurora decides** which skill fits the message — code + a pile of bugs/todos →
  `roadmap`, and it **keeps going** like a software company (CTO → TL → devs) until
  it needs you; a topic to go deep on → `research`; otherwise `write-article` and
  the rest.
- `aurora --solo` becomes a mode where you hand it a description and it **already
  knows how** — asks the right questions, drives the skills, loops until done.
- A **skill marketplace**: Auroras pull skills from a registry or a direct link,
  automatically when asked.

## The four workstreams

### A. Per-skill enable/disable (small)

- **Goal:** `/skill on|off <id>` toggles one skill; `/skill on|off` (no id) keeps
  the global switch. Disabled skills never auto-fire but can still be forced with
  `/skill use <id>`.
- **Design:** add `config.skills.disabled: []` (id list). `selectSkill` filters it
  out of candidates; `/skill list` shows a per-skill on/off marker. Persisted in
  config.
- **Plugs in:** `src/skills/corpus.js:149` (filter), `src/cli.js:1119-1140` (firing),
  `handleSkill` list/on/off branches.
- **Risk:** low. This one is genuinely v0.3.15-sized on its own.

### B. Smarter routing — message → the right active skill, or none (medium)

- **Goal:** reliably map a message's _kind_ to a skill: code+bugs+todos → `roadmap`;
  deep topic → `research`; long-form → `write-article`; else none. Today's scorer
  is keyword overlap + the intent gate; it works for distinct triggers but blurs as
  skills multiply.
- **Design:** keep the cheap scorer as the first pass; when two skills score close,
  a small model-decided tie-break (the routing-ladder doctrine: route by task,
  escalate by stakes). Author the missing **`research` skill** (wraps the 6-module
  research method) so there's something to route _to_.
- **Plugs in:** `src/skills/corpus.js` (scoring), `src/skills/intent.js` (gate),
  a new `skills/research.md`.
- **Risk:** medium — mis-routing reshapes a turn wrongly. The intent gate already
  guards "talking about vs doing"; lean on it.

### C + D — Autonomy and the skill marketplace → deferred to v0.4.1

The autonomy / `--solo` driver (the "keep going like a software company" loop) and
the skill marketplace are the two high-risk pillars. Both are **planned in full on
the `v0.4.1` future-features line**, so they don't hold the v0.3.15 wins hostage:

- **Autonomy + `--solo` driver** — the roadmap execute loop running continuously
  with hard budgets, consent gates, and an activity view (`/monitor`).
- **Skill marketplace / remote install** — pull skills from a registry or a link,
  behind a trust model (install-disabled-by-default, provenance, no silent fetch).

Full design, risks, and open decisions live in `docs/design/skills-os-v04.md` on
the `v0.4.1` branch, indexed in that branch's `docs/design/backlog.md`.

## Honest scope call — what actually fits v0.3.15

All four in one version is not realistic, and bundling the high-risk pieces with
the easy ones would hold the easy wins hostage. Proposed split:

| Version     | Contents                                                                                                                                                   | Why                                                                                                              |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **v0.3.15** | **A** (per-skill toggle) + **B** (routing + author the `research` skill) + finish the `roadmap` **execute loop** (the non-autonomous, human-gated version) | Self-contained, low/medium risk, makes "Aurora picks the right active skill" real with 3 skills to route between |
| **v0.4.1**  | **C** (autonomy + `--solo`) and **D** (marketplace) — the future-features line                                                                             | The two high-risk pillars; each needs its own safety design first (see `skills-os-v04.md`)                       |

## When this does NOT serve you / risks to respect (v0.3.15 scope)

- **More skills can route worse, not better.** Each new skill is another way the
  router can mis-fire. The intent gate and per-skill disable are the brakes.
- **Forcing a skill when none fits** turns an ordinary turn into ceremony — "none"
  must stay a valid route.

(The autonomy "token fire" and marketplace supply-chain risks live with their
design in `docs/design/skills-os-v04.md` on `v0.4.1`.)

## Open decisions (v0.3.15)

- Per-skill toggle storage: a `disabled: []` list vs a `{id: bool}` map (leaning:
  `disabled` list — sparse, simple).
- Does routing ever pick **zero** skills and just answer plainly? (Leaning: yes —
  "none" is a valid route; don't force a skill.)

(Autonomy-budget and marketplace-registry decisions are tracked in the v0.4.1 doc.)

## Build order for v0.3.15 (once approved)

1. **A** — per-skill enable/disable (small, unblocks "activate/deactivate any skill").
2. **`research` skill** + **B** routing improvements (gives the router a real choice).
3. **`roadmap` execute loop** — the human-gated implement → verify loop (no
   autonomy yet), validated on the `PRE_RELEASE` notes.

Related: `roadmap-skill.md` (the execute loop this depends on), `intent-gate.md`
(act vs discuss — routing must respect it), and `skills-os-v04.md` on `v0.4.1`
(the deferred autonomy + marketplace pillars).
