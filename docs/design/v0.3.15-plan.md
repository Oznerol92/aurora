# v0.3.15 plan — skills as Aurora's operating system (plan)

Status: **draft** (2026-06-10). Big-changes line; **plan only, no code yet.**
Scope is large enough that this doc proposes a **phased split** rather than
promising all of it in one version.

## The vision (from the user)

Aurora should run itself through **skills**, choosing the right one by what the
message is:

- Each skill can be **individually enabled/disabled**; Aurora picks among the
  _active_ ones.
- **Aurora decides** which skill fits the message — code + a pile of bugs/todos →
  `roadmap`, and it **keeps going** like a software company (CTO → TL → devs) until
  it needs you; a topic to go deep on → `research`; otherwise `write-article` and
  the rest.
- `aurora --solo` becomes a mode where you hand it a description and it **already
  knows how** — asks the right questions, drives the skills, loops until done.
- A **skill marketplace**: Auroras pull skills from a registry or a direct link,
  automatically when asked.

and one (routing) exists but is thin and needs more skills to route between.

## The four workstreams

### A. Per-skill enable/disable (small)

- **Goal:** `/skill on|off <id>` toggles one skill; `/skill on|off` (no id) keeps
  the global switch. Disabled skills never auto-fire but can still be forced with
  `/skill use <id>`.
- **Design:** add `config.skills.disabled: []` (id list). `selectSkill` filters it
  out of candidates; `/skill list` shows a per-skill on/off marker. Persisted in
  config.
- **Plugs in:** `src/skills/corpus.js:149` (filter), `src/cli.js:1119-1140` (firing),
  `handleSkill` list/on/off branches.
- **Risk:** low. This one is genuinely v0.3.15-sized on its own.

### B. Smarter routing — message → the right active skill, or none (medium)

- **Goal:** reliably map a message's _kind_ to a skill: code+bugs+todos → `roadmap`;
  deep topic → `research`; long-form → `write-article`; else none. Today's scorer
  is keyword overlap + the intent gate; it works for distinct triggers but blurs as
  skills multiply.
- **Design:** keep the cheap scorer as the first pass; when two skills score close,
  a small model-decided tie-break (the routing-ladder doctrine: route by task,
  escalate by stakes). Author the missing **`research` skill** (wraps the 6-module
  research method) so there's something to route _to_.
- **Plugs in:** `src/skills/corpus.js` (scoring), `src/skills/intent.js` (gate),
  a new `skills/research.md`.
- **Risk:** medium — mis-routing reshapes a turn wrongly. The intent gate already
  guards "talking about vs doing"; lean on it.

### C. Autonomy — "keep going until something comes up" + `--solo` driver (large)

- **Goal:** the `roadmap` **execute loop** (implement → verify, retries capped)
  running continuously across todos — the CTO/TL/dev shape — pausing only at the
  human gate or on a halt. And `aurora --solo "<description>"` that takes a brief,
  picks the skill, asks the right questions, and drives it to completion.
- **Design:** build on the `roadmap` design doc's Level 1 → 2 path
  (`docs/design/roadmap-skill.md`). Autonomy needs **stop conditions**: a per-run
  token/step budget, the verify gate, retry caps, and a halt-and-ask on ambiguity.
  `--solo` autonomy is a new run mode layered on the existing ephemeral `--solo`.
- **Plugs in:** the roadmap execute loop (new), `src/cli.js:111` (`--solo`), the
  one-shot runners / worker-borrow for role agents.
- **Risk: high.** This is where tokens run away and where "it did something I
  didn't want" lives. Needs explicit budgets, consent gates, and a visible
  activity view (ties to the parked `/monitor` idea). **Treat as its own version,
  likely v0.3.16+ / v0.4.x**, not bundled into v0.3.15.

### D. Skill marketplace / remote install (large, security-sensitive)

- **Goal:** `/skill install <url-or-name>` pulls a skill into `~/.config/aurora/skills`
  (or project-local); a registry lists installable skills; "auto-pull if asked"
  fetches on demand.
- **Design:** a skill is just a Markdown file, so distribution is easy — but **a
  skill reshapes a turn and can pin an engine**, so a malicious one is a real
  prompt-injection / supply-chain vector. Defenses, not afterthoughts:
  - **Install ≠ activate.** A pulled skill lands **disabled**; you review it
    (`/skill show`) and enable it explicitly. Never auto-run remote skills.
  - **Source pinning + provenance.** Record where each skill came from; show it in
    `/skill list`. Pin a version/hash.
  - **No silent network fetch.** "Auto-pull if asked" still confirms before
    fetching and before first use.
- **Plugs in:** `src/skills/corpus.js` (loader gains a remote source + provenance),
  a new install command, a registry format.
- **Risk: high (supply chain).** The whole feature's value is gated on the trust
  model being right. **Defer to v0.4.x**; design the trust model before any fetch
  code exists.

## Honest scope call — what actually fits v0.3.15

All four in one version is not realistic, and bundling the high-risk pieces with
the easy ones would hold the easy wins hostage. Proposed split:

| Version     | Contents                                                                                                                                                   | Why                                                                                                              |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **v0.3.15** | **A** (per-skill toggle) + **B** (routing + author the `research` skill) + finish the `roadmap` **execute loop** (the non-autonomous, human-gated version) | Self-contained, low/medium risk, makes "Aurora picks the right active skill" real with 3 skills to route between |
| **v0.3.16** | **C** — autonomy + `--solo` driver, with budgets/consent/activity view (depends on `/monitor`)                                                             | High risk; needs the execute loop proven first                                                                   |
| **v0.4.x**  | **D** — marketplace, after a written trust model                                                                                                           | Supply-chain risk; belongs with the multi-provider line                                                          |

## When this does NOT serve you / risks to respect

- **Autonomy without budgets is a token fire.** "Keep going until something comes
  up" must have a hard step/token ceiling and a halt-on-ambiguity rule, or a vague
  brief burns money producing wrong work. This is the single biggest risk.
- **A marketplace is a supply-chain surface.** A skill is a prompt; a hostile one
  is prompt injection that reshapes every matching turn. Install-disabled-by-default
  and explicit review are non-negotiable, not polish.
- **More skills can route worse, not better.** Each new skill is another way the
  router can mis-fire. The intent gate and per-skill disable are the brakes.
- **`--solo` is ephemeral today** (no store). An autonomous `--solo` that produces
  real work needs a place to put artifacts — reconcile with the store model first.

## Open decisions

- Per-skill toggle storage: a `disabled: []` list vs a `{id: bool}` map (leaning:
  `disabled` list — sparse, simple).
- Does routing ever pick **zero** skills and just answer plainly? (Leaning: yes —
  "none" is a valid route; don't force a skill.)
- Autonomy budget unit: steps, tokens, wall-clock, or all three (leaning: all
  three, whichever trips first).
- Marketplace registry: a flat list repo vs a real index. Defer with the feature.

## Build order for v0.3.15 (once approved)

1. **A** — per-skill enable/disable (small, unblocks "activate/deactivate any skill").
2. **`research` skill** + **B** routing improvements (gives the router a real choice).
3. **`roadmap` execute loop** — the human-gated implement → verify loop (no
   autonomy yet), validated on the `PRE_RELEASE` notes.

Related: `roadmap-skill.md` (the execute loop this depends on), `intent-gate.md`
(act vs discuss — routing must respect it), and the parked `/monitor` idea (the
activity view autonomy in v0.3.16 will need).
